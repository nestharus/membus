# F-E6-20 grouped write path

kv/1 remains minor0 with unchanged MBK1 records. This implements docs/PLAN.md4 and supersedes KV1.md9's historical slice1 ticket-per-waiter description.

Optional diagnostic opcode9 IO_METRICS uses the ordinary deadline/op_id/namespace prefix and no suffix, returning threeLEu64values: current-process logical append bytes, actual File::write calls (including interrupted attempts), and sync attempts. It is additive under minor0; old servers return unsupported2, and existing HELLO/HEALTH layouts remain unchanged. Counters exclude startup epoch I/O, replay reads, transport I/O and resident heartbeat I/O. Partial append bytes count even when its outcome is uncertain.

Four persistent append workers each own a stripe file. Admission charges complete queued representations (fingerprint+value+128bytes), at most1024outstanding mutations and queue_bytes/4chargedbytes per stripe, queue_bytes overall. Oversize/saturated admission returns busy6 before pending key/version/retry identity insertion. The state_limit_bytes default8GiB includes replayed log bytes and exact pending record lengths. New durable records beyond the bound return capacity7 before admission; existing state stays readable. Failed I/O keeps a conservative disk reservation until restart.

os writes publish after complete append without waiting for flush. flush writes publish after their complete-record offset is covered by sync. One device worker gathers for flush_ms after its first waiter arrives. It selects one stripe, initially up to64waiters/144192recordbytes (one larger record allowed), then syncs that handle. Sync covers its whole earlier append extent: every already queued waiter with covered end offset can complete, including more than64waiters. Actual acknowledgement cohort is bounded by admitted1024outstanding items and the charged stripe byte bound;144192bytes is a selection budget rather than a physical flush-byte cap. Waiters arriving during sync are conservatively handled later. Physical device bytes are unmeasured.

flush_ms sets both the gather window and the minimum device interval between completing one sync attempt and starting the next. At50ms steady attempts are limited to20/s plus the first attempt; latency adds queueing and OSsync time. This is an initial configurable policy, not an owner-approved optimum. A serial caller issuing one flush request and waiting still pays one window per call; batches, pipelining and concurrent calls supply overlap.

Distinct batch keys overlap using at most32scoped helpers; one batch executes per Store. Simultaneous batches return busy6 before any item admission. Same-key items and replies keep input order; batches remain non-atomic. The batch gate never participates in gets/individualwrites. Store drops close and join its five durable workers. Partial appends fence their stripe, so no complete record follows a torn tail. Sync failure poisons the stripe and marks durable admissions read_only. Committed gets use only the memory map: no append/queue/batch/flush lock or file I/O.

Path-valued test environment variables MEMBUS_TEST_PAUSE_PARTIAL and MEMBUS_TEST_PAUSE_SYNC create a marker and pause at partial append or sync-worker entry. Leave unset in normal operation. The sync marker proves a worker boundary before the sync call, not residence within Windows FlushFileBuffers; actual kernel-in-flight kill coverage remains unverified.

Measurement and located dispositions are under the F-E6-20 report and REVIEW-DISPOSITION.md. Same-key order and reply order, covering flush groups, complete-record state cap, empty-value queue bounds and previous protocol/replay behavior have Rust regression checks.
